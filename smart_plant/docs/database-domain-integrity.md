# 数据库领域完整性决策

## 已落地边界

- 数据库结构与参考数据只通过 Flyway 演进，Java 启动过程禁止执行 DDL/DML。
- `user.role_id` 是用户角色唯一事实源，不允许恢复 `user_role` 或进行双写。
- `farm.longitude/latitude` 与 `plot.longitude/latitude` 是坐标唯一事实源；`coordinate` 是只读生成列，仅用于兼容现有管理端和移动端响应。
- `notification.ref_type/ref_id` 仅表示同一消息对多个接收人的投递分组，不承担数据库业务外键职责。
- 农事任务、预警事件、维护消息分别使用 `task_id`、`alert_id`、`maintenance_message_id` 作为受数据库约束的业务引用。
- 四类 IoT 采集表的 `data_status` 必须为 1 或 2，湿度、pH、光照、流量、压力等指标在数据库入口执行基本物理范围校验。

## 发布规则

1. 备份生产数据库，在同版本副本执行 `flyway validate` 和 `flyway migrate`。
2. 结构迁移由独立、固定版本的 Flyway CLI/容器作业执行，成功后再滚动发布应用；生产应用实例使用默认的 `FLYWAY_ENABLED=false`，禁止多个实例同时承担迁移职责。应用内迁移仅用于本地开发和测试。
3. 已发布迁移不可修改。修复只能增加新版本，生产环境始终保持 `clean-disabled=true`。
4. 执行 V5 前必须确认通知引用无孤儿、坐标不存在无法解析的单边数据、遥测值满足新增约束。
5. 迁移后核对 Flyway 版本、外键、CHECK 约束以及核心接口回归测试结果。

## 后续规模化演进

当前每类遥测数据只有 2 条，立即替换四套接口的收益低于发布风险。本阶段先在现有表建立强约束。达到持续高频写入、设备类型快速增长或需要跨指标统一查询时，再使用兼容迁移引入“采集批次 + 指标明细”模型，完成双写校验、历史回填、读流量切换后再退役分类表；不得一次性改表并同时切换三个客户端。

SaaS 租户边界不应通过给少数表临时增加 `tenant_id` 实现。确定租户、用户和农场归属规则后，应采用扩展—回填—双读校验—强制非空—租户唯一键的分阶段迁移，并同步改造鉴权上下文和所有查询条件。
