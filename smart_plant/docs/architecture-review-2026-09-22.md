# smart_plant / smart_farm / farm 与实际数据库审查

审查日期：2026-09-22。范围：当前工作区源代码、配置、迁移、隔离测试，以及本地配置连接的 MySQL `smart_plant`。本文没有修改业务代码、配置或数据库；构建和测试产生了常规构建产物。

## 结论与边界

当前项目已经形成农业业务管理平台的主要功能，具备 Controller / Service / Mapper 分层、JWT、BCrypt、RBAC、资源归属校验、Flyway、任务执行记录和部分乐观锁。优先工作应是修复身份与数据边界、库存并发、真实设备执行闭环以及交付验证，暂不需要拆成微服务。

存在上线阻断项：短信验证码直接返回、匿名自选农场主即可获得成员身份、管理端可逆保存密码、业务附件匿名读取，以及当前出入库实现的并发丢失更新。其余重要问题涉及部署地址、验证码、多端会话、IoT 控制、查询规模、AI 长事务、消息推送和工程测试。

本文区分三种证据：代码可确认的行为；本地实际数据库查询结果；尚未经过压测、真机或硬件验证的风险。不把当前开发配置等同于生产配置，不把迁移成功记录等同于全量 schema/checksum 校验通过，也不把测试通过等同于安全验收通过。

页面验证只实际打开了两个前端的登录界面；其他页面的 UI 判断来自源码，未完成全部角色、分辨率和真机交互验收。未调用真实设备、发送短信或付费 AI 接口，也未利用发现的问题登录其他账号。

## 二、上线前必须修复的事项

### P0-01：短信登录没有证明手机号所有权

**证据：** [ClientAuthServiceImpl.java:260](<D:/Project/Spring Boot/Intelligent_Agriculture/smart_plant/src/main/java/com/smart_plant/smart_plant/service/impl/ClientAuthServiceImpl.java:260>) 的 `sendSmsCode` 在第 292 行直接返回验证码；`ClientAuthController` 的 `/sms-code/login` 和 `/sms-login` 在匿名白名单内。`farm/pages/login/code_index.vue:114` 还将验证码打印到控制台并显示 Toast，没有生产环境隔离。

**影响：** 对已绑定手机号、且允许登录客户端的有效账号，知道手机号即可取得验证码并完成登录，不需要接触真实手机。后续限流与 BCrypt 不能弥补此身份验证缺口。

**改进：** 生产环境禁用模拟发码或接入实际短信投递，响应仅返回发送结果和等待时间；按手机号、IP、设备控制频率；验证码设置 TTL、次数上限并保证一次性消费。测试码只能存在于明确隔离的测试环境。`updateProfile` 目前也接受新手机号直接写入，应统一收口到经过验证的换绑流程；注册时填写手机号同样需要明确“未验证/已验证”状态。

**验收：** 生产响应和日志不出现验证码；未证明手机号所有权不能登录、绑定或换绑；验证码并发重复消费只能成功一次。

### P0-02：匿名注册可以直接加入任意可选农场主

**整改状态（2026-09-22）：已完成代码整改。** 普通用户和技术人员匿名注册现在只创建禁用账号与待审核入场申请，不再写入成员绑定；农场主只能审核本农场申请，管理员可跨农场审核。批准后才在同一事务中建立绑定并启用账号，拒绝保持禁用，撤销会删除绑定、禁用账号并撤销登录会话。管理端已增加申请列表、批准、拒绝和撤销入口；普通用户编辑与状态接口会拒绝绕过审核。新增 V35 数据库迁移及反向测试，覆盖仅知道 farmOwnerId 无法获得权限、跨农场审批失败、重复审批失败、撤销后绑定和会话失效。部署时需先执行 V35；历史绑定缺少来源记录，无法自动判断是否经过授权，需由管理员和农场主复核。

**证据：** `ClientAuthServiceImpl.java:134` 允许提交 `roleCode=user/technician` 和 `farmOwnerId`，只检查农场主存在、角色正确且启用，然后直接创建启用用户，并在第 189/191 行写入成员绑定表。匿名接口还能列出可选农场主。`DataPermissionServiceImpl.currentClientOwnerId()` 将绑定关系直接作为普通用户可访问的农场范围，仓库、监控和环境服务复用此范围。

**影响：** 接口查询虽然有归属过滤，但攻击者可以通过注册建立“合法”的归属关系，继而读取对应农场的业务信息。这是成员加入机制的问题，单纯加强列表 WHERE 条件无效。技术人员是否能处理具体故障仍取决于实际派单，不应夸大为注册后可以修改所有设备。

**改进：** 加入农场采用农场主发出的限时邀请或管理员审批；注册产生待审核关系，审核前不能进入资源权限计算。技术人员身份及指派也需可信授权。移除匿名任意选择内部组织的入口，或仅允许发起不授予权限的申请。

**验收：** 仅知道 farmOwnerId 无法读取目标农场；撤销成员关系后权限及时失效；跨农场读取和加入流程均有反向测试。

### P0-03：管理端把真实密码可逆保存到浏览器

**整改状态（2026-09-22）：已完成代码整改。** 删除密码编码、持久化和回填，将选项改为“保持登录”，复用已有 access/refresh token 存储和刷新机制。管理端启动及退出时直接删除旧密码缓存，登录成功后清空表单密码。新增回归测试覆盖启动清理、勾选/未勾选的令牌存储、页面逻辑重载及退出清理。下述证据保留为整改前审查记录。

**证据：** `smart_farm/src/views/LoginView.vue:61` 使用 `btoa(encodeURIComponent(...))`，第 102 行对象包含 `password`，第 109 行持久化到 localStorage。

**影响：** Base64 是编码，能直接还原。浏览器脚本、XSS 或本机存储泄露会暴露可长期使用的原始密码。

**改进：** 删除密码持久化和回填逻辑，清理旧的 remembered-login 数据；仅记住用户名，长期会话依靠受控刷新令牌。“记住密码”文案同步改为“保持登录”。浏览器令牌存储方式调整应同时设计 SameSite、CSRF 和跨域策略。

### P0-04：业务附件的静态读取没有资源授权

**整改状态（2026-09-22）：已完成代码整改。** 删除 `/uploads/**` 匿名白名单，仅保留登录页所需的 `/uploads/system-settings/**` 公共品牌资源；其他业务上传统一要求有效 JWT 或受限的 HttpOnly 资源 Cookie。聊天附件改由专用下载控制器返回，读取时按数据库中的消息、专家咨询参与人、农场聊天参与人和当前有效成员绑定重新授权，成员解绑后旧 URL 立即失效；尚未发送的附件只允许上传者预览。移动端聊天图片和文件改为携带 Bearer Token 的受控下载。响应增加 `no-store`、`nosniff` 和安全的 Content-Disposition，并通过 V36 为附件授权查询增加索引。新增回归测试覆盖匿名白名单收窄、上传者预览、会话参与人读取、无关用户拒绝及成员解绑后拒绝。

**证据：** `WebMvcConfig.java:46` 将整个 `/uploads/**` 列为匿名路径，第 92 行直接映射磁盘目录。`ConsultAttachmentService` 在其中保存聊天图片与文档。现有上传 Cookie 验证代码不改变这些路径已被白名单跳过的事实。

**影响：** 取得附件 URL 的人可以不登录读取；UUID 只能减少猜测，无法约束 URL 被转发后的访问，也无法在移除成员后撤销访问。公用品牌图片与私有聊天附件不能使用同一公开策略。

**改进：** 明确公用与私有资源范围；私有附件通过资源归属校验的下载接口，或短期签名地址访问。可以使用 Cookie、受控 Blob 或签名 URL 支持图片展示，无需因此公开整个目录。

### P0-05：出入库并发会造成库存余额与流水不一致

**整改状态（2026-09-22）：已完成代码整改。** 新增出入库在同一数据库事务中先使用 `SELECT ... FOR UPDATE` 锁定物资行，再基于锁内库存计算并写入余额和流水；已停用或已软删除物资不能继续出入库，库存更新和流水插入均检查影响行数。管理端为每次出库生成业务请求幂等键，后端通过 V37 唯一约束及锁内查询保证相同请求重试只返回原流水，复用幂等键提交不同业务会被拒绝。新增回归测试覆盖锁内库存快照、重复请求、更新失败和停用物资边界。部署时需先执行 V37，并在独立测试库继续执行真实并发压测。

**证据：** `WarehouseServiceImpl.java:274` 先普通查询物资，基于旧库存计算结果，再调用 `updateStock`；`WarehouseItemMapper.xml:131` 是 `SET stock_qty = #{stockQty}`，没有行锁、版本条件或原子扣减条件，也没有检查该更新的影响行数。

**影响示例：** 库存为 10，两个事务分别出库 7，各自读到 10，都通过“库存不能小于零”检查，最终库存可能为 3，但流水累计出库 14。普通 `@Transactional` 不能自动防止此模式。

**改进：** 优先在当前单库事务内对库存行加锁后计算和写入流水；也可使用带库存下限条件的原子更新，但必须确保流水 before/after 与真实变更一致。检查更新行数；为重复提交增加业务请求幂等键。

**验收：** 独立测试库并发出库不能超卖，余额与流水一致；重复请求不重复扣减；软删除或状态变化期间不能出现只写流水而不更新库存。

## 四、smart_farm 管理端

1. **P1：生产环境地址不可直接发布。** `.env.production` 的 API 地址仍为 `http://127.0.0.1:8080/smart_plant`。部署后访问者浏览器会请求其自己的电脑；HTTPS 页面还会涉及混合内容。改成部署环境地址或同源代理，并确保后端允许实际业务域名。当前 CORS 白名单主要是 localhost 和私网地址。
2. **P1：权限与会话更新缺少统一生命周期。** 刷新并发问题见前文；本地缓存的权限在后台变更后可能保持旧 UI。统一刷新用户信息，区分 401、403、业务失败，避免重复提示与多次跳转。后端校验仍应是最终权限边界。
3. **P2：页面复用不足。** expert/ListView 1071 行、plot/AddOrUpdate 1043 行、warehouse/ListView 1015 行。优先提取已重复的筛选、分页、图片上传、详情弹窗和状态展示；统一页面框架，避免各页面重复持有头部、侧栏和布局逻辑。不要为复用而搭建复杂低代码平台。
4. **P2：登录表单可访问名称不完整。** 实际可访问性树中账号、密码输入没有清楚的名称；源码主要用 placeholder，缺少可见 label。补充 label、字段错误关联和键盘焦点样式，保留已有密码切换按钮的 aria-label。
5. **P2：状态展示与成功反馈应对应实际业务。** 对设备开关、计划应用、云台等，区分“配置已保存”“指令待下发”“设备已确认”“执行失败”，不能用统一成功 Toast 掩盖尚未接入硬件的事实。

已有懒加载、Element Plus 按需组件和 Vite 分组，本次构建成功，不能再沿用旧报告中“所有页面首屏加载”的结论。没有测量 LCP / INP 或全部后台页面，不能给出实际性能评分。

1. **P1：API 地址写死开发网段。** `utils/request.js:4` 默认私网 IP，H5 第 18 行固定 `http://当前主机:8080`。生产域名、TLS、反向代理和真机网络切换需要明确配置，不能依赖用户手改本地缓存。
2. **P1：refresh token 未使用。** `utils/auth.js:18` 明确只做持久化；401 统一清登录。应完成服务端客户端刷新契约，并合并并发过期处理，避免多个 Toast 和重复 reLaunch。
3. **P1：仓库列表最多返回 200 条，却在前端本地搜索。** `WarehouseServiceImpl.java:209` 固定取第一页 200 条；`pages/service/wareHouse.vue:114` 对已加载 items 过滤。超过上限后统计总数可能正确，但搜索不到后续物资。改为服务端筛选与分页，并提供加载更多。
4. **P2：AI 历史附件名称丢失。** V27 和实库已有 `ai_chat.file_name`，但 AiChat 实体、Mapper 插入/查询未映射；发送时返回 fileName，读取历史却固定返回“文件附件”。补齐 DTO→实体→SQL→历史响应链路，回归“发送后刷新页面仍显示原文件名”。
5. **P2：聊天全量加载。** `FarmChatMessageMapper.selectBySessionId` 没有分页；专家聊天页每 10 秒刷新详情。随会话增长增加流量与渲染成本，宜采用按消息 ID 的游标分页、增量补拉与推送结合。
6. **P2：存在看似可操作但未实现的入口。** QQ/微信登录只显示 Toast；密码登录页的协议入口也只显示标题 Toast；语音发送提示尚未接入。应接通真实流程，或隐藏/明确禁用，避免用户把展示入口当作已交付能力。
7. **P2：占位符与自动填充冲突。** 密码登录页第 11/24 行使用独立 text 模拟 placeholder；本次 H5 截图可见自动填充值与占位文案重叠。优先原生 placeholder 和稳定 label，回归浏览器自动填充、密码管理器和切换密码可见状态。
8. **P2：交互语义和触控区域不足。** 多处 text/view 充当返回、切换登录、协议复选框和图标按钮，缺少 accessible name/role/state；登录页可访问性树未识别出清晰的操作按钮集合。补充平台支持的语义与标签，扩大返回等小图标触控区域，在真机验证键盘弹起、安全区和长文本。
9. **P2：请求失败、无数据、离线与陈旧数据应有不同展示。** 例如 farm_list 的失败主要依靠全局 Toast，页面可能保留空列表或旧数据；应提供持久错误状态、重试及最后更新时间。现场作业应先做好失败反馈和可重试，再按实际需求增加离线能力。

视觉方向建议沿用已有农业绿色/青色，不必推倒重做。两端应统一状态含义、业务术语和信息层级；管理端突出筛选、操作与表格效率，移动端突出待办、异常、现场处理和可读性。以上后台页面建议属于源码审查结论，尚未完成多设备视觉验收。

## 六、数据库 smart_plant

### 应保留的基础

Flyway、外键、CHECK、唯一约束、DECIMAL、设备+采集时间索引和部分版本锁已经存在。没有证据要求立即迁移数据库、分库分表或增加时序数据库；现有数据规模很小。

### 优先改进

| 优先级 | 问题 | 建议 |
|---|---|---|
| P1，生产准入 | 当前本地应用配置使用 root@localhost，拥有全实例广泛权限 | 运行账号只授权业务所需 DML；迁移账号独立承担 DDL。这里只证明本地配置，不推断线上也使用 root |
| P1 | 库存更新缺少并发控制，流水不能作为可靠对账基础 | 同事务锁定余额、写流水、检查影响行数；补业务请求唯一键 |
| P1 | 设备历史观测按当前设备关联地块与所有者展示 | `EnvironmentDataMapper` 从当前 iot_device 取 plot_id/user_id，设备服务允许改地块。设备迁移后历史会按新归属解释。明确是禁止有历史设备迁移，还是保存部署区间/采集时归属；历史迁移要保留证据，不能猜测回填 |
| P2 | 遥测采集缺少可见的消息去重键 | 现有 device_id+collect_time 是普通索引，不能阻止重传重复。按设备协议选择消息序列/消息 ID 的唯一性，不宜未经定义就把同秒记录全部判为重复 |
| P2 | alert 和通用 notification 的幂等依靠先查后插 | 根据事件窗口、来源、接收人建立业务唯一约束，并定义关闭后再触发规则 |
| P2 | 库存汇总直接 SUM(stock_qty) | 不同物资单位可不同，把“袋/千克/件”相加缺少业务意义。按单位或品类分组，或使用明确估值方法；计价时区分初始价、最新价、移动加权价 |
| P2 | `ai_chat.file_name` 已迁移但没有应用读写 | 增加字段级契约回归，防止“数据库变了，界面短暂显示正确，但持久化丢失” |
| P2，增长前准备 | 日志、消息、遥测无统一可见的保留/归档作业 | 先定义保留周期、按批清理、备份与恢复要求；有真实规模和执行计划后再决定分区或专用时序存储 |
| P2 | 索引有单列与同前缀复合索引并存 | 结合外键依赖与实际 EXPLAIN/写入压力判断冗余，不能只按名称或重复前缀直接删除 |

迁移文档版本表只列到 V5，而实库已到 V34。V1 在当前库是 baseline，不代表本次已验证从空库执行 V1–V34。应在独立数据库验证空库初始化、历史库升级、迁移校验和备份恢复；不可通过修改已发布迁移文件来修补历史。

## 八、建议实施顺序与验收门槛

**第一阶段：关闭安全和数据损坏入口。** 完成 P0-01 至 P0-05；移除生产模拟短信、匿名自动加入组织、密码持久化和私有附件公开读取；库存余额与流水具备并发一致性。真实数据库应用账号按最小权限配置。

**第二阶段：补齐可用性与真实业务闭环。** 配置双端生产地址；统一 refresh 和多端会话政策；修复验证码；设备指令有 ACK 和超时；统一异常事件与处置；最新遥测查询限量；AI 网络等待移出事务。

**第三阶段：稳定交付和扩展。** 测试数据库隔离，修复失效测试并补关键行为测试；补齐文件名持久化、分页、聊天增量；统一状态/错误 UI 与可访问性；建立可重复部署、备份恢复和数据保留流程。

**架构建议：** 保持单体部署，按认证权限、农场种植、IoT、任务预警、仓库、咨询与文件等领域逐步收敛包和职责。当前先利用数据库事务、已有 Redis 和已有命令表解决明确问题；只有真实吞吐、隔离或团队边界证明需要时，再引入独立网关、队列或拆分服务。
