# Smart Plant / Smart Farm 企业级架构审查报告

审查日期：2026-09-05

审查范围：

- `smart_farm`：Vue 3 + TypeScript + Element Plus 管理端
- `smart_plant`：Spring Boot 4 + Java 21 + MyBatis 后端
- 本机 `smart_plant`：MySQL 8.4 实际数据库

## 一、执行结论

当前系统已经形成“用户与权限—农场—地块—种植批次—作物生长阶段—设备与采集数据—AI 识别—农事任务—通知”的主要业务链，作为单体式智慧水培管理系统，功能覆盖较完整，代码也可以正常构建和运行。但它仍处于“功能型项目”向“生产级平台”过渡的阶段：业务边界不够统一、数据库演进方式存在高风险、前端复用不足，安全配置与集群化能力尚未达到企业生产标准。

## 二、预警事件管理是否保留

### 结论：必须保留，不执行删除

`alert_event` 应当是系统的“可处置事件中心”，负责统一记录事件来源、等级、阈值、触发时间、处理人、处理过程和处理结果。它与其他三个相近模块的合理边界如下：

| 模块 | 应承担的职责 | 是否可替代预警事件 |
|---|---|---|
| 设备故障 `iot_device_fault` | 设备故障事实、持续时间、维修责任与结果 | 否；它只覆盖设备域 |
| 维护消息 `maintenance_message` | 将设备故障转换为面向农场主/技术人员的维护内容快照 | 否；它是内容发布层 |
| 通知 `notification` | 接收人、投递、已读、消息入口 | 否；它是通知投递层，不应承载事件生命周期 |
| 预警事件 `alert_event` | 多来源异常的统一分级、受理、处理、忽略、闭环和统计 | 是事件主记录 |

保留的直接证据：

1. AI 识别处置服务会创建 `AlertEvent`，再以 `alert_event` 作为通知关联对象。
2. `notification.alert_id` 对 `alert_event.id` 存在外键，通知查询还会联表读取预警标题与等级。
3. 表内已经具备事件中心所需的来源、指标、阈值、等级和处理状态字段，删除会使 AI 异常处置退化为不可追踪的普通消息。
4. 当前 0 条实库记录只说明事件生产链没有被充分接入，不能证明领域能力不需要。

### 当前主要缺陷

页面宣称支持环境异常、设备异常、任务逾期、摄像头异常、AI 识别异常、库存预警 6 类，但代码检索确认只有 AI 识别链调用 `AlertEventService.createIfAbsent`。另外五类目前没有统一写入事件表：

- 传感器异常直接创建 `farm_task` 和 `notification`，绕过 `alert_event`；
- 设备故障创建维护消息和通知，绕过 `alert_event`；
- 没有发现任务逾期调度器；
- 没有发现摄像头离线/采集失败事件生产器；
- 仓库只有预警数量字段，没有库存预警事件生产器。

这会造成统计一直为空、来源规则不一致、同一异常在多个页面无法关联、处理状态不能统一回写。

### 推荐闭环

所有异常应先幂等写入 `alert_event`，再按规则生成任务或故障，并通过 `notification` 投递：

`采集/检测 -> 规则判定 -> alert_event -> 分派或生成 farm_task / iot_device_fault -> notification -> 受理/处理 -> 关闭事件`

预警事件原则上不应提供普通“删除”动作。业务人员应使用“关闭/忽略/误报”并保留审计记录；仅系统管理员可以按数据保留策略归档，避免破坏追溯性。

## 三、功能合理性审查

### 合理部分

- 农场、地块、种植批次、作物、生长阶段之间的业务层次基本合理。
- 生长阶段保存温湿度、pH、EC、光照和灌溉参考值，传感器异常可以据此产生农事任务，具备领域价值。
- AI 识别记录、AI 处置方案、农事任务、预警、通知之间已经存在初步联动。
- 设备故障到维护消息再到指定农场主/技术人员通知，职责分层较清晰。
- RBAC、数据范围和资源归属校验已经进入服务层，不只是前端隐藏按钮。
- 登录日志、操作日志、页面访问日志和 Prometheus 指标为审计与运维提供了基础。

### 不合理或不完整部分

1. **预警中心名义统一、实际割裂（P0）**：6 类预警只有 1 类真实接入。
2. **消息类功能重叠（P1）**：农事消息底层复用农事任务，系统公告、维护消息、通知又各自建模；需要明确“业务对象、消息模板、投递记录”的三级模型。
3. **缺少任务逾期机制（P0）**：数据库定义了逾期状态和日志动作，但未发现定时扫描或延迟任务。
4. **IoT 数据接入仍像后台 CRUD（P1）**：未见 MQTT、设备鉴权、消息去重、乱序处理、离线补传、采集质量标记和设备影子；不适合大规模真实设备。
5. **本地文件存储（P1）**：图片写入项目 `uploads`，单机可用，但多实例部署会丢失一致性，应迁移对象存储并保存对象键、哈希、MIME、尺寸等元数据。
6. **集群状态不安全（P0）**：Token 黑名单、登录会话、登录限流均为内存实现，多实例之间不一致，重启后状态丢失，应放入 Redis。
7. **命名边界含混（P2）**：`smart_farm` 实际是管理端，`smart_plant` 同时承载管理端和客户端 API；建议改为 admin-web / api-server 等职责名称。
8. **前端存在无路由菜单（P1）**：“系统配置”“短信验证码管理”有权限和菜单文字，但没有 path，点击无业务结果。

## 四、后端与安全审查

### 优点

- Controller、Service、Mapper 分层明确，MyBatis SQL 可追踪。
- JWT access/refresh token、JTI、登出黑名单、账户/IP 失败锁定、BCrypt 密码已经实现。
- `CurrentUserContext` 在请求完成后清理，避免线程复用造成串号。
- 多个写操作使用事务，且数据权限进入服务层。
- 统一响应和异常处理、请求超时、健康检查与 Prometheus 已具备。

### 关键风险

1. **配置中存在固定数据库口令、JWT 默认密钥和默认密码（P0）**。必须使用环境变量或密钥管理系统；生产启动时若仍是默认值应直接失败。
2. **生产配置仍指向 127.0.0.1 HTTP（P0）**，`require-https` 为 false。应通过同域反向代理访问 `/api` 并强制 TLS。
3. **Actuator、Swagger、上传目录匿名开放（P0/P1）**。生产仅应开放必要的健康端点，Prometheus 放在内网并鉴权；接口文档默认关闭；上传文件需访问控制或签名 URL。
4. **缺少 Bean Validation 实现（P1）**。测试启动日志明确提示没有 Jakarta Validation Provider，应加入 validation starter，并使用请求 DTO + `@Valid`，避免直接绑定实体。
5. **运行期自动建表/改表（P0）**。项目包含多个 `ApplicationRunner` SchemaInitializer，启动时执行 DDL，甚至删除外键/列。生产环境不可审计、不可可靠回滚，也会导致多实例并发启动冲突。应统一迁移到 Flyway 或 Liquibase。
6. **MyBatis SQL 全量输出（P1）**。当前配置使用 stdout SQL 日志，生产会产生大量日志并可能泄露业务内容。
7. **Druid 每次借连接校验（P2）**。`test-on-borrow=true` 会增加高并发下数据库压力，建议关闭并依赖 idle 校验。
8. **前端记住密码为 Base64 类编码（P0）**。登录页注释也承认浏览器无法安全保存明文，但当前仍把可逆密码存入 localStorage。应只保存用户名，长期登录依靠旋转的 refresh token；更理想是 HttpOnly/Secure/SameSite Cookie。
9. **刷新 token 并发控制缺失（P1）**。多个请求同时 401 时会并发刷新并重复跳转，需要 single-flight 队列。
10. **大量超大 Service/SFC（P2）**。后端部分服务接近 600 行，前端多个页面超过 800—1200 行，变更风险和测试成本较高。

## 五、数据库审查

### 实库概况

- MySQL 8.4.0；55 张 InnoDB 表；统一 `utf8mb4_0900_ai_ci`。
- 所有表均存在主键；共有 88 个外键。
- 当前约 743 行、约 5.03 MB，属于功能验证规模，尚不能代表高并发性能。
- 核心数据：8 用户、2 农场、2 地块、1 种植批次、7 设备、4 农事任务、45 通知、2 条已软删除设备故障、0 预警事件。
- 30 个后端测试全部通过；集成测试在真实本地业务库事务中运行并回滚，未发现残留测试行，但事务回滚不会保证自增值不推进，也无法隔离锁和启动初始化影响。

### 合理部分

- 业务主表普遍有主键、唯一键、状态、创建/更新时间和必要外键。
- 使用 DECIMAL 保存测量值、经纬度和金额，避免浮点误差。
- 种植批次连接作物、地块和生长阶段，能保存历史种植上下文。
- 预警表保存触发时的指标值和阈值，维护消息保存发布快照，适度反范式是合理的审计设计。
- 表与索引对常用的用户、设备、地块、状态、时间查询已有覆盖意识。

### 主要问题

1. **数据库版本源不唯一（P0，已整改）**：已建立 Flyway V1 基线及后续版本迁移，并删除 7 个启动初始化器；后续禁止 Java 启动代码执行结构或参考数据变更。
2. **用户角色双模型（P0，已整改）**：已确认系统采用单用户单角色模型，以 `user.role_id` 为唯一事实源，并通过 Flyway V2 删除 `user_role`。
3. **通知关联语义不清（P1，已整改）**：V5 明确 `ref_type + ref_id` 仅为投递分组键，任务、预警、维护消息使用独立外键，并增加配对、类型和引用一致性约束。
4. **坐标重复（P2，已整改）**：V5 确立 longitude/latitude 为唯一事实源，`coordinate` 改为数据库只读生成列以兼容现有 API，并禁止半对坐标。
5. **IoT 时序数据按设备类别分表（P1）**：环境、水质、灯、水泵各有独立表，短期直观，新增传感器类型必须改表、实体、Mapper、Service、Controller 和页面。规模扩大后建议“统一采集记录 + 指标明细”或接入时序数据库，并按时间分区/冷热分层。
6. **状态字段语义不统一（P2）**：`status` 在不同表中分别表示启停、业务状态、软删除状态，容易误用。软删除应统一为 `deleted_at/is_deleted`，业务状态使用专名。
7. **外键删除规则偏保守且不统一（P2）**：当前有 NO ACTION、RESTRICT、CASCADE、SET NULL 四类，需要形成主数据、事务数据、日志数据的统一保留策略。
8. **索引存在重叠迹象（P2）**：多个单列索引与以同列开头的复合索引同时存在。应基于真实慢查询、执行计划和写入成本逐个裁剪，不能只按字段“看起来会查”就加索引。
9. **缺少租户边界（P1）**：如果目标是 SaaS，多数表仅有 user_id/farm_id，没有 tenant_id、租户唯一键和租户级审计，不能直接安全演进为多租户平台。

## 六、管理端 UI/UX 审查

### 优点

- 登录页采用左右分栏、品牌区和清晰表单，视觉层次完整；管理页使用统一侧栏、页头、卡片、表格和分页。
- 颜色、阴影、间距、状态标签和统计卡片整体一致。
- 列表普遍支持分页、加载态、筛选、确认提示和固定操作列。
- 多数复杂页面提供 1280/960/720 像素断点，侧栏在窄屏可收起。
- 权限同时影响侧栏显示和路由访问，用户体验与后端鉴权基本一致。

### 主要问题

1. **筛选条件被全局 CSS 强制隐藏（P0）**：`.filter-form > .el-form-item:nth-of-type(n + 4)` 让所有列表最多显示前三个条件。预警页定义的状态、来源、时间三个条件实际不可见，也没有“更多筛选”，属于功能不可达。
2. **导航信息架构过重（P1）**：侧栏约 18 个一级入口和大量二级入口，业务、配置、运营、审计混排。建议按“生产运营、设备监控、AI 与知识、消息协作、系统治理”重组，并提供菜单搜索/常用入口。
3. **页面布局和 CSS 大量复制（P1）**：几乎每个列表页重复 100vh shell、统计卡、筛选卡、表格卡和响应式样式。应抽象 `AdminLayout`、`QueryPanel`、`DataTablePage`、`StatusTag`、`ResponsiveDrawer`。
4. **单文件组件过大（P1）**：最大页面 1276 行；业务、请求、映射、表格、弹窗和 CSS 耦合，难以测试维护。建议使用 composable、子组件和领域 API 类型拆分。
5. **首屏包过大（P1）**：生产构建主 JS 约 1.79 MB、gzip 516 KB。路由大多静态 import，应全部页面级懒加载，并拆分 Element Plus、图表及公共依赖。
6. **行内操作过载（P1）**：预警页单行固定 320px，显示详情、处理中、已处理、忽略、删除 5 个动作。应突出一个主动作，其余放入“更多”菜单，并按当前状态过滤不可用动作。
7. **移动端细节不足（P1）**：预警详情抽屉固定 640px，未对 720px 以下设置 100%；复杂表格只能横向滚动，移动端可改为卡片/关键字段模式。
8. **可访问性不足（P2）**：部分图标按钮有 aria-label，但大量操作依赖颜色标签和图标，需补充键盘焦点、文本标签、对比度和错误关联。
9. **前端缺少自动化测试（P1）**：没有发现 Vitest/组件测试/E2E 配置。建议至少覆盖登录刷新、权限路由、关键 CRUD、预警处置和响应式断点。
10. **登录页存在运行时组件告警（P2）**：实际打开页面时，Element Plus 提示复选框 `trueValue/falseValue` 期望字符串或数字但收到布尔值。当前不阻断登录，但说明组件 API 与依赖版本未完全对齐，应改用该版本支持的布尔绑定属性并纳入控制台零告警检查。
